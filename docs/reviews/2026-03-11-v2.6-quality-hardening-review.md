## 二、SPEAR 详细评分

### S（安全）— 9.0/10

**问题列表：**

- **[MEDIUM]** `libs/core/src/message/part.cpp:78` — `role_from_string()` 对无效输入静默返回 `Role::User` 而非抛出异常

  > 数据库中若存储了损坏或恶意构造的 role 字段，反序列化时会静默转换为 `User` 身份，可能导致权限混淆。
  > **修复建议**：
  >
  > ```cpp
  > Role role_from_string(std::string_view str) {
  >     auto it = str_to_role.find(str);
  >     if (it == str_to_role.end()) {
  >         throw std::invalid_argument(
  >             fmt::format("Unknown role string: '{}'", str));
  >     }
  >     return it->second;
  > }
  > ```

- **[LOW]** `libs/network/src/http_client.cpp:465` — `set_ssl_verify(false)` 仅输出 WARN 日志，不阻止调用
  > **修复建议**：在 Release 模式下使该函数成为 no-op，仅 `#ifdef DEBUG` 生效。

**扣分**：MEDIUM(-1.0) = **-1.0**

### P（性能）— 8.0/10

**问题列表：**

- **[MEDIUM]** `libs/core/src/snapshot/snapshot.cpp:300` — `scan_files()` 将所有匹配文件的**完整内容**读入内存（`file_contents` map）

  > 大型 monorepo 中 `file_contents` 可能占用 GB 级内存，存在 OOM 风险。
  > **修复建议**：仅在需要 diff 时按需读取内容，`scan_files` 默认只保存 hash：
  >
  > ```cpp
  > // 仅保存 hash，不缓存内容
  > data.file_hashes[path_str] = compute_file_hash(path);
  > ```

- **[LOW]** `libs/core/src/snapshot/snapshot.cpp:228-251` — `is_excluded()` 中路径前缀匹配每次调用产生临时 `std::string` 对象

  > **修复建议**：使用 `std::string_view` 和 C++20 `starts_with()` 避免临时分配。

- **[LOW]** `libs/core/src/session/session_loop.cpp:348-351` — `estimate_tokens()` 以 `text.size()/4 + 1` 估算 token，多字节字符场景误差极大
  > **修复建议**：区分 ASCII/UTF-8 字符分别计算，或引入 tiktoken 近似算法。

**扣分**：MEDIUM(-1.0) + LOW(-0.5) + LOW(-0.5) = **-2.0**

### E（错误处理）— 6.5/10

**问题列表：**

- **[MEDIUM]** `libs/core/src/message/part.cpp:54` — `part_type_from_string()` 对未知类型静默降级为 `PartType::Text`

  > 数据库存储了新版本写入的新类型时，反序列化静默损坏数据，无任何警告。
  > **修复建议**：至少记录 WARN 日志；在严格场景下抛出 `std::invalid_argument`。

- **[MEDIUM]** `libs/utils/src/crypto_utils.cpp:476-480` — `sha256_file()` 对超大文件或不可读文件返回空字符串 `""`，无法区分三种错误原因（NotFound / TooLarge / IOError）

  > `stop_tracking()` 会将超大文件（返回 `""`）误判为"已修改"，产生虚假 diff。
  > **修复建议**：引入强类型错误返回：
  >
  > ```cpp
  > enum class FileHashError { NotFound, TooLarge, IOError };
  > using FileHashResult = std::variant<std::string, FileHashError>;
  > FileHashResult sha256_file(const std::filesystem::path& p);
  > ```

- **[MEDIUM]** `libs/core/src/session/session_loop.cpp:300-321` — `execute_tool()` 未捕获 C++ 异常，工具抛出异常直接传播至 `run()`，导致整个 session 崩溃

  > **修复建议**：
  >
  > ```cpp
  > try {
  >     return tool->execute(input, ctx);
  > } catch (const std::exception& e) {
  >     return tool::ToolResult::error("ToolException", e.what());
  > } catch (...) {
  >     return tool::ToolResult::error("ToolException", "Unknown exception");
  > }
  > ```

- **[LOW]** `libs/storage/src/sqlite_database.cpp:410-416` — `SQLiteTransaction::~SQLiteTransaction()` 中 `rollback()` 抛出异常后 `active_` 未重置，导致 `is_active()` 持续误报
  > **修复建议**：catch 块中强制 `active_.store(false)`。

**扣分**：MEDIUM(-1.0) × 3 + LOW(-0.5) = **-3.5**

### A（架构）— 7.0/10

**问题列表：**

- **[MEDIUM]** `libs/core/src/session/session_loop.cpp:304, 399-412` — `execute_tool()` 和 `build_tool_definitions()` 均直接依赖 `tool::ToolRegistry::instance()`（全局单例），形成**隐式依赖**

  > 测试时无法注入 Mock ToolRegistry，`E2E-08b` 中需通过 `remove("repeat_tool")` 清理全局状态，架构缺陷已在测试中显现。
  > **修复建议**：在 `SessionLoop` 构造阶段注入 `ToolRegistry*`，默认值指向全局单例。

- **[MEDIUM]** `libs/core/src/session/session_loop.cpp:353-393` — `build_llm_messages()` 在 `messages_mutex_` **之外**读取 `agent_`，存在**数据竞争（UB）**

  > 若另一线程同时调用 `set_agent()`，产生未定义行为。
  > **修复建议**：添加专用 `agent_mutex_`，在 `build_llm_messages()` 入口处 snapshot `agent_`：
  >
  > ```cpp
  > std::shared_ptr<agent::Agent> local_agent;
  > {
  >     std::lock_guard<std::mutex> lock(agent_mutex_);
  >     local_agent = agent_;
  > }
  > // 后续使用 local_agent
  > ```

- **[LOW]** `libs/core/src/snapshot/snapshot.cpp:170-173` — `SnapshotManager::instance()` 是 Meyer's Singleton，全局可变状态导致单元测试间互相污染

  > **修复建议**：暴露 `reset_for_testing()` 静态方法。

- **[LOW]** `libs/storage/src/migration.cpp:62` — `get_executed()` 使用 `std::find`（O(n)），整体 O(n×m) 复杂度
  > **修复建议**：将 `executed` 转换为 `std::unordered_set<std::string>`。

**扣分**：MEDIUM(-1.0) × 2 + LOW(-0.5) × 2 = **-3.0**

### 纠偏项（4 处）

**纠偏 1：`LoopResult::DoomLoop` 枚举值不存在**

本报告引述 2.6.5 计划文档时提及"结果必须为 `DoomLoop`"，但实际 `LoopResult` 枚举只有 `Continue / Stop / Compact / Error` 四个值（`session_loop.cpp:11-19`）。doom loop 触发时返回 `LoopResult::Error`（`session_loop.cpp:251`）。

- 计划文档 2.6.5 中的验收标准 `结果必须为 DoomLoop` **有误**
- 本报告 Fix-T2 修复建议写的是 `CHECK(result == session::LoopResult::Error)`，**方向正确**
- 已有 E2E-08b 完整验证了 doom loop 返回 `Error`，作为 Fix-T2 的替代验证

**纠偏 2：`scan_files()` 缓存内容是有意设计**

`scan_files()` 中 `file_contents` 的填充（`snapshot.cpp:300`）是为了给 `stop_tracking()` 在检测文件修改时提供 `old_content`（见 `snapshot.cpp:395-399`）。这是一个**有意的设计取舍**，不是无意引入的内存浪费。

P0 修复建议"删除内容缓存"会破坏 `PatchResult` 中 `FileChange::old_content` 的功能。**正确的优化策略应为**：

1. 添加 `SnapshotOptions::max_cache_size_mb` 上限配置（默认 50MB）
2. 或为超大目录提供"仅 hash 模式"，明确不提供 old_content diff

**纠偏 3：`part_type_from_string` 静默降级不属于 2.6 需求范围**

本报告将此问题列于 E 维度，定性合理，但在需求覆盖度表中未体现（因为 2.6 计划没有要求修改此函数）。**这是新发现的独立问题**，不应计入 2.6.5 覆盖度统计。

**纠偏 4：ERR-01/ERR-07 测试实际上不验证"重试"**

`SessionLoop` 本身没有内置重试逻辑（见 `session_loop.cpp:209-213`，error 直接返回 `LoopResult::Error`）。计划文档 2.6.5 Fix-T1/T3 要求 `call_count >= 3` 的前提是"2 次错误 + 1 次成功"，但实际 `SessionLoop` 收到 error response 后**立即返回 Error**，不会重试。

因此 Fix-T1/T3 要求 `call_count >= 3` 这个断言，**只有当重试逻辑存在时才能成立**。这揭示了一个更深层的问题：**要么 2.6.5 的测试计划本身就超前于实现（重试机制尚未实现），要么重试逻辑确实存在但在 `RetryManager` 层而非 `SessionLoop` 层**。这需要进一步确认 `RetryManager` 是否被 `SessionLoop` 使用。

> **建议**：在修复 Fix-T1/T3 之前，先确认 `RetryManager` 与 `SessionLoop` 的集成状态，避免写出永远无法通过的测试断言。
