### ⚠️ 遗留问题（源码层）

**[HIGH] 内置 Agent BuildAgent / ExploreAgent / PlanAgent 为占位**

计划 2.16 标记为 A 级完成，但实际：

```cpp
// build_agent.cpp / explore_agent.cpp / plan_agent.cpp
// Build/Explore/Plan agent is a placeholder for now
return ExecuteResult::ok(fmt::format("... processed..."));
```

三个 Agent 只返回字符串，不执行真实 LLM 调用，评级 A 存疑。

**[MEDIUM] agent_loader.cpp 动态生成为占位**

```cpp
// agent_loader.cpp line 265
// This is a placeholder implementation
// In a full implementation, this would use LLM to generate agent configuration
```

`generate_agent()` 当前只做简单字符串 slug 生成，未接入 LLM。

**[HIGH] 权限系统旁路（SessionLoop 未注入 ask_permission）**

二次核实发现：权限规则定义完整（`permission.cpp`，各工具均有 `ctx.ask_permission` 调用），但 `SessionLoop::execute_tool()`（line 700）构建 `ToolContext` 时**从未设置 `ask_permission` 回调**：

```cpp
// session_loop.cpp:700
tool::ToolContext ctx;
ctx.session_id = session_.id();
ctx.message_id = ...;
ctx.agent       = ...;
ctx.call_id     = call_id;
ctx.abort_flag  = abort_flag_;
ctx.working_directory = ...;
// ask_permission 未设置 → 所有工具走 allow 分支
```

结果：所有工具（read/write/edit/bash/glob/grep/list）因 `if (!ctx.ask_permission)` 检查直接跳过交互式确认，权限系统实际处于**旁路状态**，`permission.cpp` 中的规则引擎从未触发。

> OpenCode 对比：通过 EventBus `permission.asked` 事件 → ACP `requestPermission()` → 用户确认完整闭环。Turbot 当前缺少 ACP → SessionLoop → ToolContext 的权限注入链路。

```
              → build_llm_messages()    ✅（含系统提示词 + 工具 schema）
              → Plugin.trigger(chat.params / chat.headers)  ✅
              → LLM::stream()           ✅（含 repairToolCall 容错）
              → RetryManager::with_retry()  ✅（429/5xx 自动重试）
              ↓ 有 tool_calls：
              → execute_tool()          ✅（含 question / skill 等）
              → 死循环检测              ✅
              → Plugin.trigger(text.complete)  ✅

  → Session.revert()                    ✅（Part 粒度撤销 + snapshot）
```

| E 错误处理 | **B+** | RetryManager 集成 SessionLoop；repairToolCall 工具名容错；统一 try-catch                        |
