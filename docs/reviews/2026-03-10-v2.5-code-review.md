## Critical 问题（必须修复，共 4 项）

### C-1: `active_tracking_count()` 数据竞争

| 属性   | 详情                                                          |
| ------ | ------------------------------------------------------------- |
| 文件   | `libs/core/include/turbot/core/snapshot/snapshot.hpp:124-126` |
| 严重度 | Critical（数据竞争 → UB）                                     |

**问题**：`active_tracking_count()` 声明为 `noexcept` 但未加锁读取 `snapshots_`，与 `start_tracking()`/`stop_tracking()` 存在数据竞争，在多线程环境下可能导致未定义行为。

```cpp
// 问题代码
[[nodiscard]] size_t active_tracking_count() const noexcept {
    return snapshots_.size();  // 未加锁！
}

// 修复
[[nodiscard]] size_t active_tracking_count() const noexcept {
    std::lock_guard<std::mutex> lock(mutex_);
    return snapshots_.size();
}
```

### C-2: `MockProvider::chat_stream()` 持锁调用回调 → 潜在死锁

| 属性   | 详情                                  |
| ------ | ------------------------------------- |
| 文件   | `tests/mock/mock_provider.hpp:88-132` |
| 严重度 | Critical（死锁）                      |

**问题**：`chat_stream()` 在持有 `mutex_` 的情况下调用用户传入的 `callback`。若回调（如 E2E-05 中的流中断回调）调用任何 `MockProvider` 成员方法（如 `call_count()`），会发生递归死锁。

```cpp
// 问题代码
[[nodiscard]] core::provider::ChatResponse chat_stream(...) override {
    std::lock_guard<std::mutex> lock(mutex_);  // 持有锁
    // ...
    if (callback) {
        for (const auto& chunk : stream_chunks_) {
            callback(event);  // 回调中可能调用 call_count() → 再次尝试加锁 → 死锁!
        }
    }
}

// 修复
[[nodiscard]] core::provider::ChatResponse chat_stream(...) override {
    std::vector<std::string> local_chunks;
    core::provider::ChatResponse final_response;
    {
        std::lock_guard<std::mutex> lock(mutex_);
        call_count_++;
        local_chunks = stream_chunks_;  // 锁内拷贝
        // 准备 final_response ...
    }
    // 锁已释放，再调用 callback
    if (callback) {
        for (const auto& chunk : local_chunks) { /* send event */ }
    }
    return final_response;
}
```

#### C-3: 工具结果消息角色错误 + `Role` 枚举缺失 `Tool` 值

| 属性   | 详情                                                                                                    |
| ------ | ------------------------------------------------------------------------------------------------------- |
| 文件   | `libs/core/src/session/session_loop.cpp:269` + `libs/core/include/turbot/core/message/part.hpp:220-224` |
| 严重度 | Critical（语义错误 → LLM 上下文损坏）                                                                   |

**问题一**：工具执行结果消息使用 `Role::User`，导致 LLM 收到的对话历史中工具结果以"用户发言"形式出现，破坏对话结构和上下文语义。

**问题二**：`Role` 枚举当前只有 `User`/`Assistant`/`System` 三个值，**没有 `Role::Tool`**，不支持标准的工具结果消息角色。

```cpp
// part.hpp:220 - 当前 Role 枚举
enum class Role {
    User,      ///< User message
    Assistant, ///< AI assistant message
    System     ///< System message
    // 缺少: Tool
};

// 修复步骤：
// 1. 在 part.hpp 中扩展 Role 枚举
enum class Role {
    User,
    Assistant,
    System,
    Tool       ///< Tool result message (新增)
};

// 2. 在 session_loop.cpp:269 使用正确角色
core::Message tool_msg(session_.id(), core::Role::Tool, tc.name, "", "");

// 3. 在 build_llm_messages() 中增加 Tool 角色处理
case core::Role::Tool: {
    auto content = msg.get_text();
    result.push_back(llm::LLMMessage::tool(content, msg.info().agent));
    break;
}
```

> **连带影响**：`role_to_string()`、`role_from_string()` 需同步更新；`build_llm_messages()` 中的 `switch` 需增加 `Role::Tool` 分支。

### C-4: 使用 OpenSSL 已弃用 API

| 属性   | 详情                                                     |
| ------ | -------------------------------------------------------- |
| 文件   | `libs/core/src/snapshot/snapshot.cpp:160-186`            |
| 严重度 | Critical（弃用 API，OpenSSL 3.x 编译警告，未来移除风险） |

**问题**：`compute_file_hash()` 使用 `SHA256_CTX`/`SHA256_Init`/`SHA256_Update`/`SHA256_Final`，这些 API 在 OpenSSL 3.0 中已被弃用。项目 `libs/utils` 中已有使用现代 EVP API 的 `crypto::sha256()` 函数。

```cpp
// 修复：利用已有的 turbot::utils::crypto::sha256()
// 需在 libs/utils 中扩展 sha256_file(const std::filesystem::path&) 方法
#include <turbot/utils/crypto_utils.hpp>

std::string SnapshotManager::compute_file_hash(const std::filesystem::path& path) {
    auto content = read_file_content(path);
    return turbot::utils::crypto::sha256(content);
}
```

## Major 问题（应该修复，共 7 项）

### M-1: `start_tracking`/`stop_tracking` 持锁执行 IO 操作

| 文件 | `libs/core/src/snapshot/snapshot.cpp:320-427` |
| ---- | --------------------------------------------- |

持锁期间执行完整目录遍历和文件读取，锁阻塞时间可达数秒，阻塞所有并发 tracking 调用。应将 IO 操作移出锁范围，仅在更新 `snapshots_` 容器时加锁。

---

### M-2: `is_doom_loop()` input 参数未使用

| 文件 | `libs/core/src/session/session_loop.cpp:322-330` |
| ---- | ------------------------------------------------ |

接受 `input` 参数但完全不使用，相同工具名但不同参数的调用会被错误判为死循环（如 `read_file("/a")` 和 `read_file("/b")`）。应将参数哈希（如 `input.dump()`）纳入比较。

---

### M-3: `is_excluded()` 每次调用重新编译正则

| 文件 | `libs/core/src/snapshot/snapshot.cpp:223-271` |
| ---- | --------------------------------------------- |

每次调用在循环内对每个含通配符的 pattern 重新构造 `std::regex`。`stop_tracking` 对每个文件都调用一次，大型项目下性能极差。应在 `SnapshotData` 中预编译正则缓存。

---

### M-4: count+at 双重查找惯用法

| 文件 | `libs/core/src/snapshot/snapshot.cpp:399-401, 413-415` |
| ---- | ------------------------------------------------------ |

```cpp
// 问题（两次查找）
data.file_contents.count(path_str) > 0 ? data.file_contents.at(path_str) : ""

// 修复（一次查找）
auto it = data.file_contents.find(path_str);
it != data.file_contents.end() ? it->second : ""
```

---

### M-5: `build_llm_messages()` 持锁期间构建消息

| 文件 | `libs/core/src/session/session_loop.cpp:359-378` |
| ---- | ------------------------------------------------ |

持有 `messages_mutex_` 期间执行完整消息构建（含字符串操作），锁持有时间不必要延长。应先在锁内拷贝 vector，再在锁外构建 LLM 消息。

---

### M-6: `total_usage_`/`total_cost_` 无锁外部访问

| 文件 | `libs/core/include/turbot/core/session/session_loop.hpp:127-130` |
| ---- | ---------------------------------------------------------------- |

`total_usage()` 和 `total_cost()` 标记为 `noexcept` 但无锁读取，当外部线程读取时可能出现竞争。应改为原子类型或文档明确说明非线程安全。

---

### M-7: MockProvider `timeout_behavior` 字段设置但从未使用

| 文件 | `tests/mock/mock_provider.hpp:187-190, 237-238` |
| ---- | ----------------------------------------------- |

`set_timeout_behavior()` 设置了 `timeout_after_` 和 `timeout_then_succeed_`，但 `chat()` 和 `chat_stream()` 中完全没有使用这两个字段，导致 ERR-02 超时测试实际上无法验证超时恢复行为。

## 测试质量问题（共 3 项）

### T-1: PERSIST-07 串行测试冒充并发测试

| 文件 | `tests/integration/persistence_test.cpp:332-356` |
| ---- | ------------------------------------------------ |

测试名为 "Concurrent message creation"，实际是完全串行的 `for` 循环，没有任何并发。是误导性测试，应重命名或使用真实 `std::thread`/`std::async`。

---

### T-2: E2E-07 重试测试验证强度不足

| 文件 | `tests/integration/e2e_test.cpp:169-172` |
| ---- | ---------------------------------------- |

配置了 2 次错误+1 次成功的序列，但只断言 `call_count() >= 1`，无法证明重试实际发生。应断言 `result == LoopResult::Stop` 且 `provider->call_count() == 3`。

---

### T-3: E2E-08 死循环检测验证逻辑模糊

| 文件 | `tests/integration/e2e_test.cpp:192-196` |
| ---- | ---------------------------------------- |

`CHECK(provider->call_count() <= config.doom_loop_threshold + 1)` 既没有验证返回了 `LoopResult::Error`，也没有明确验证死循环被触发。
