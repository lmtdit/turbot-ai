# ADR-003: 目录架构规范

## 元数据

| 属性     | 值         |
| -------- | ---------- |
| 状态     | ✅ 已批准  |
| 日期     | 2026-03-08 |
| 决策者   | 架构团队   |
| 影响版本 | v1.0       |

## 背景

Turbot-AI 作为 C++ AI Agent 框架，需要清晰的目录结构来：

1. **模块解耦**: 各模块独立编译、独立测试
2. **职责分离**: 库、应用、测试、文档明确分离
3. **版本演进**: 支持 v1.0/v2.0/v3.0 分阶段开发
4. **可维护性**: 新成员快速理解项目结构

## 决策

### 1. 项目根目录结构

```
turbot-ai/
├── apps/                    # 应用程序
├── libs/                    # 核心库
├── tests/                   # 测试代码
├── third_party/             # 第三方依赖
├── docs/                    # 文档
├── build/                   # 构建配置
├── cmake/                   # CMake模块
├── CMakeLists.txt           # 根CMake配置
├── CMakePresets.json        # CMake预设
├── conanfile.py             # Conan依赖配置
├── .clang-format            # 代码格式配置
└── .clang-tidy              # 静态分析配置
```

### 2. 库分层架构

采用四层库架构：

```
libs/
├── core/                    # 核心库 - 业务核心逻辑
├── storage/                 # 存储层 - 数据持久化
├── network/                 # 网络层 - HTTP/WebSocket通信
└── utils/                   # 工具库 - 通用工具函数
```

**依赖关系**：

```
        ┌─────────────┐
        │    apps     │
        └──────┬──────┘
               │
    ┌──────────┼──────────┐
    │          │          │
    ▼          ▼          ▼
┌───────┐  ┌───────┐  ┌───────┐
│ core  │  │storage│  │network│
└───┬───┘  └───┬───┘  └───┬───┘
    │          │          │
    └──────────┼──────────┘
               │
               ▼
        ┌───────────┐
        │   utils   │
        └───────────┘
```

**依赖规则**：

- `utils` 是基础层，不依赖其他库
- `core`、`storage`、`network` 可依赖 `utils`
- `apps` 可依赖所有库
- 库之间尽量避免横向依赖

### 3. 单个库的标准结构

```
libs/<library>/
├── CMakeLists.txt           # 库的CMake配置
├── include/
│   └── turbot/<library>/    # 公共头文件
│       ├── export.hpp       # 导出宏定义
│       └── ...              # 其他头文件
└── src/                     # 源文件实现
    └── ...
```

**命名规范**：

| 项目       | 规范                                  |
| ---------- | ------------------------------------- |
| 命名空间   | `turbot::<library>`                   |
| 头文件     | `#include <turbot/<library>/xxx.hpp>` |
| CMake 目标 | `turbot_<library>`                    |

### 4. Core 库模块化设计

Core 作为核心库，按功能模块组织：

```
libs/core/include/turbot/core/
├── common/              # 通用模块
├── config/              # 配置模块
├── event/               # 事件模块
├── message/             # 消息系统
├── provider/            # AI提供商系统
├── permission/          # 权限系统
├── tool/                # 工具系统
├── agent/               # Agent系统
├── session/             # 会话系统
│
│ === v2.0 核心流程完善 ===
│
├── prompt/              # Prompt生成系统 📋
├── llm/                 # LLM调用层 📋
├── skill/               # Skill系统 📋
│
│ === v3.0 协议系统 ===
│
├── mcp/                 # MCP协议 📋
├── lsp/                 # LSP协议 📋
└── acp/                 # ACP协议 📋
```

### 5. 测试目录集中化

所有测试集中存放在 `tests/` 目录：

```
tests/
├── unit/                    # 单元测试
│   ├── config_test.cpp
│   ├── provider_test.cpp
│   └── ...
├── integration/             # 集成测试
└── test_integration.cpp     # 测试入口
```

**设计原则**：

- 不在各库目录下创建 tests 子目录
- 测试文件命名：`<模块名>_test.cpp`
- 测试标签：`[<library>][<module>]`

### 6. 版本化模块演进

按版本分阶段实现模块：

| 版本 | 阶段          | 核心模块                                           |
| ---- | ------------- | -------------------------------------------------- |
| v1.0 | 多 Agent 架构 | utils, core 基础, storage, network, agent, session |
| v2.0 | 核心流程完善  | prompt, llm, skill, session 扩展                   |
| v3.0 | 协议系统开发  | mcp, lsp, acp                                      |

### 7. 模块解耦设计原则

每个 Plan 阶段实现的模块必须满足：

| 原则      | 要求               |
| --------- | ------------------ |
| 独立编译  | 模块可独立编译     |
| 独立测试  | 测试覆盖率 ≥ 85%   |
| 接口隔离  | 模块间通过接口交互 |
| Mock 友好 | 支持依赖注入       |

## 理由

### 为什么选择四层库架构？

| 备选方案           | 拒绝理由                     |
| ------------------ | ---------------------------- |
| 单一库             | 职责混乱，编译时间长         |
| 两层（core+utils） | storage/network 无法独立演进 |
| 五层以上           | 过度设计，增加复杂度         |

### 为什么测试集中存放？

| 备选方案             | 拒绝理由               |
| -------------------- | ---------------------- |
| 各库自带 tests 目录  | 测试分散，难以统一管理 |
| tests/unit 镜像 libs | 路径冗余，不必要       |

### 为什么按版本分阶段？

| 备选方案       | 拒绝理由                 |
| -------------- | ------------------------ |
| 一次性实现所有 | 工作量过大，风险高       |
| 无版本规划     | 缺乏里程碑，难以追踪进度 |

## 影响

### 正面影响

- 新模块有明确的放置位置
- 模块边界清晰，降低耦合
- 版本规划清晰，便于迭代开发
- 测试集中管理，覆盖率易统计

### 风险

- 模块划分需要持续维护
- 版本间依赖需要仔细管理

### 兼容性

- 现有目录结构保持稳定
- 新模块按规范添加

## 验收标准

每个 Plan 完成时必须满足：

| 验收项   | 标准               |
| -------- | ------------------ |
| 编译     | 模块独立编译通过   |
| 单元测试 | 测试覆盖率 ≥ 85%   |
| 测试通过 | 100% 测试通过      |
| 静态分析 | clang-tidy 无警告  |
| 内存检查 | ASan/UBSan 无问题  |
| 文档更新 | 目录架构文档已更新 |
